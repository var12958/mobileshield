# Mobile Network Malware Traffic Detection (Phase 1)

Production-grade, leak-proof Machine Learning pipeline for Android network malware traffic classification using the **CICAndMal2017** dataset.

---

## 1. Project Overview & Scope

This project implements **Phase 1: Offline Machine Learning & Network Traffic Forensic Modeling** for detecting Android mobile malware network communications.

### Core Objectives
1. **Experiment A (Binary Classification)**: Classify bidirectional network flows into `BENIGN` vs. `MALWARE_ASSOCIATED`.
2. **Experiment B (Multiclass Classification)**: Classify malicious flows into 4 canonical categories: `ADWARE`, `RANSOMWARE`, `SCAREWARE`, and `SMSMALWARE` alongside `BENIGN`.
3. **Leakage-Proof Evaluation**: Eliminate experimental data leakage by grouping train/validation/test splits strictly at the **APK capture session level (`sample_id`)** and evaluating on an unseen **Zero-Day Malware Family Holdout**.

### Explicit Scope Restrictions (Phase 1)
- **Malware Communication, NOT Device Compromise**: Models classify traffic signatures associated with malware; they do not claim to identify human adversaries or prove kernel compromise.
- **No General Network Intrusion Claims**: CICAndMal2017 contains endpoint mobile malware communication only. It contains **zero** instances of DoS/DDoS, Nmap port scanning, or SSH/FTP brute force.
- **Offline Baseline Only**: High offline accuracy does not prove real-time detection without live gateway packet capture (deferred to Phase 2).

## 2. Dataset Forensic Audit Summary

- **Source**: Canadian Institute for Cybersecurity (CIC), University of New Brunswick (UNB).
- **Physical Makeup**: **2,126 CSV files**, **1.22 GB** (1,311,278,522 bytes), **2,616,579 network flow records**.
- **Raw PCAP & APK Status**: **0 PCAPs** and **0 APKs** exist in the local dataset. Files represent pre-extracted flow feature tables generated by **CICFlowMeter** (`*.pcap_ISCX.csv`).
- **Feature Count**: 84 flow features + 1 `Label` column.
- **Header Anomaly**: Column 40 and Column 61 both had the header `'Fwd Header Length'`. Preprocessing disambiguates Column 61 to `'Fwd Header Length.1'`.
- **Zero-Variance Features Dropped (12)**: Bulk transfer metrics (`Fwd Avg Bytes/Bulk`, `Bwd Avg Bulk Rate`, etc.) and inactive TCP flags (`Bwd PSH Flags`, `Fwd URG Flags`, `Bwd URG Flags`, `RST Flag Count`, `CWE Flag Count`, `ECE Flag Count`).
- **Identifier Leakage Columns Dropped (6)**: `Flow ID`, `Source IP` (`10.42.0.x`), `Destination IP`, `Source Port`, `Destination Port`, and `Timestamp`.

## 5. Measured Empirical Results

### Experiment A: Binary Classification (`BENIGN` vs. `MALWARE_ASSOCIATED`)

*Evaluated on Held-Out Test Set (47,400 flows) and Zero-Day Unseen Families Holdout (6,750 flows):*

| Model | Test F1 | Test Accuracy | Benign FPR (%) | Zero-Day Holdout Recall (%) | Inference Latency | Throughput |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Baseline (Logistic Reg.)** | 0.3148 | 53.64% | 46.50% | 55.19% | 0.62 ms/flow | 1,560,793 flows/s |
| **Random Forest (Champion)** | **0.3609** | **77.10%** | **23.63%** | **42.24%** | 56.55 ms/flow | 13,776 flows/s |
| **Extra Trees** | 0.3440 | 76.28% | 24.47% | 40.22% | 51.26 ms/flow | 13,833 flows/s |

> **Champion Selection:** **Random Forest** was selected as the overall balanced baseline for its lower false-positive rate on benign traffic (23.63% vs 36.44% for LightGBM). However, for high-throughput live network environments, **LightGBM** provides superior streaming throughput (135K flows/sec) and higher zero-day recall (57.26%).

## 6. Scientific Data Leakage Insights

Standard academic literature frequently claims **>99% F1-score** on CICAndMal2017. Our empirical findings demonstrate that such results are an artifact of **data leakage**:
1. When flows are randomly shuffled at the row level, flows from the *same* APK execution appear in both train and test sets, allowing models to memorize transient socket ports, burst timing patterns, and CDN endpoints.
2. Under our **leak-proof group-aware split (grouped by unique APK sample ID)**, the true generalization F1-score is **0.36 to 0.37**, reflecting the real difficulty of separating encrypted mobile malware C2 traffic from modern benign app communication using Layer 3/4 flow summaries alone.
3. This finding proves why behavioral flow detection must be supplemented by host-level signals or hybrid network intrusion models in production.

## 7. Next Steps for Phase 2: Live Mobile Packet Pipeline

To transition from Phase 1 offline models to a live Android intrusion detection system:
1. **Authorized Wi-Fi Hotspot Gateway**: Establish a Windows Mobile Hotspot gateway on the monitoring laptop to capture decrypted unicast Layer 3/4 IP traffic from the phone.
2. **Streaming Flow Aggregator**: Deploy `nfstream` or `cicflowmeter` daemon with a 5–15 second active subflow timeout to extract the identical 65 features without identifier leakage.
3. **Modern Benign Baseline Data**: Capture 1–2 hours of modern Android 14/15 benign traffic to recalibrate against 2017 temporal decay (TLS 1.3 / QUIC / DoH).
4. **General Network Intrusion Hybridization**: Ingest **CIC-IDS2017** or **CSE-CIC-IDS2018** to provide coverage for DoS/DDoS, port scanning, and brute-force attacks.

## 8. Secure Relay and Production Deployment

The backend requires three operator-provided values: `ADMIN_API_TOKEN` and
`RELAY_SECRET` must each be exactly 64 lowercase hexadecimal characters
generated from at least 32 random bytes; `DEVICE_PAIRING_CODE` must be a
one-use operator-issued 64-character lowercase hexadecimal code generated
from at least 32 random bytes. Missing or weak values prevent the API and dashboard from
starting. Keep these values in a protected deployment secret store or a
permission-restricted `.env` file that is never committed.

If `.env` is missing or empty, create it from PowerShell with separate
cryptographically random values. This command does not print the generated
credentials:

```powershell
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
function New-Secret {
    $bytes = New-Object byte[] 32
    $rng.GetBytes($bytes)
    return ([BitConverter]::ToString($bytes)).Replace('-', '').ToLowerInvariant()
}
$settings = @(
    "ADMIN_API_TOKEN=$(New-Secret)"
    "RELAY_SECRET=$(New-Secret)"
    "DEVICE_PAIRING_CODE=$(New-Secret)"
)
[System.IO.File]::WriteAllLines(
    (Join-Path $PWD '.env'),
    $settings,
    [System.Text.Encoding]::ASCII
)
$rng.Dispose()
icacls .env /inheritance:r /grant:r "$($env:USERDOMAIN)\$($env:USERNAME):(R,W)"
```

The API, dashboard, and Windows relay process load this root `.env`; the
Compose file also reads the same values. `.env` is ignored by Git. Start the
local backend and dashboard in separate PowerShell windows from the project
root:

```powershell
python -m uvicorn src.companion_api:app --host 127.0.0.1 --port 8000
```

```powershell
python -m streamlit run src/dashboard.py --server.address 127.0.0.1 --server.port 8501
```

Connect an authorized phone over USB debugging. Replace `<serial>` with the
value from `adb devices -l`; `adb reverse` maps the phone's loopback port 8000
to the laptop's loopback port 8000:

```powershell
adb devices -l
adb -s <serial> reverse tcp:8000 tcp:8000
adb -s <serial> reverse --list
adb -s <serial> install -r android_companion\bin\mobileshield_companion.apk
```

Use separate generated values for the admin token, relay secret, and pairing
code. Enter them into the protected backend environment; give the relay secret
to the Windows agent using a protected environment/secret store. The pairing
code is consumed once when the Android app enrolls. Rotate it before enrolling
another device. Packet tokens are unique per device and their hashes are stored
in the persistent `device_auth` volume. Device tokens are returned only at
enrollment and stored in the app's private preferences; uninstalling the app
removes its token, so re-enrollment requires a new pairing code.

### Encrypted Windows-to-AWS path

The Windows agent uses HTTPS with normal certificate and hostname verification
for non-loopback targets, and does not follow redirects. Plain HTTP is accepted
only for loopback endpoints. A deployment without an HTTPS reverse proxy can
use an SSH local forward instead:

```powershell
ssh -N -L 127.0.0.1:8000:127.0.0.1:8000 <verified-deploy-user>@<verified-aws-host>
```

The Compose file binds backend and dashboard ports to the AWS loopback
interface. With the SSH forward active, configure the Windows relay target as
`http://127.0.0.1:8000` and set up the phone's `adb reverse tcp:8000 tcp:8000`.
The phone's localhost traffic is forwarded to the Windows host, then carried
through SSH to the backend. `adb reverse` itself is only the phone-to-host
forward; it is not the Windows-to-AWS encrypted transport. Do not expose
backend port 8000 directly to the public internet. Use an HTTPS proxy with
valid certificates instead if a public relay endpoint is required.

### Preflight, rollout, and rollback

Before rollout, record the deployed container's immutable image ID/digest,
architecture, runtime user, port bindings, and mounts on the actual deployment
host. Confirm the `captures` and `device_auth` named volumes are retained and
backed up. Do not use the mutable `latest` tag as a rollback reference.

```powershell
docker compose ps
$cid = docker compose ps -q backend
docker inspect --format '{{.Image}} {{.Config.Image}} {{.Config.User}} {{json .HostConfig.PortBindings}} {{json .Mounts}}' $cid
docker image inspect --format '{{.Id}} {{.Os}}/{{.Architecture}} {{json .RepoDigests}}' mobileshield:latest
docker volume ls
```

Verify the actual deployment username and SSH host from the approved inventory
before substituting the placeholders above. The safe rollout order is: back up
the persistent volumes and record the current immutable image; verify the new
image architecture and configuration in staging; deploy the pinned new image
without removing named volumes; confirm health, an empty-device relay heartbeat,
and the authenticated dashboard; then test enrollment and packet/PCAP behavior
with the physical phone. Roll back by redeploying the recorded prior image ID or
registry digest with the same Compose configuration and preserving both named
volumes. The repository does not contain the currently deployed digest, AWS
username, or host, so it cannot supply a concrete digest-specific rollback
command.

Do not infer physical-device detection or genuine packet capture from an empty
heartbeat, API unit tests, or a diagnostic model flow. Those require validation
with the physical phone and deployed backend.
